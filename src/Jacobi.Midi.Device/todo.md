## Message exchange

- [ ] **Message exchange for schemas without an address map** (a small redesign of the API). The exchange (`MessageExchange`, `DeviceSession`) is built on the address map: it finds, builds and recognises every message through it (`MessageExchange.MapOf`, `AddressMap.Split`, `AddressMap.Message`, `AddressProtocol.CreateMessage`, `AddressMap.TryReadData`). The exchange files are already generic: they name messages and events, no addresses. A device whose dumps are ordinary schemas (e.g. Korg dumps selected by a function code, see `docs/analysis`) cannot be exchanged. The design is decided (see [docs/decisions.md](../../docs/decisions.md), *Device messages without an address map*): a base layer of device messages (`Jacobi.Midi.Device.Messages`) with message maps per root (`IMessageMap`), created by an ordered chain of providers (`IMessageMapProvider`: address first, the default dump provider last); the exchange and the session work on the interfaces only. Each stage below builds and passes the tests on its own:
  - [ ] Stage 1: `AddressProtocol` finds the messages that carry a root with the open-choice lookups of Jacobi.BinarySerializer (`SchemaSet.FindOpenChoices`, `SchemaSet.FindDocument`, `ExecutionPlan.FindOpenChoices`, `GetOpenChoiceBodies`) instead of its own matching (`CarriesContract`, `IsDataOf`, `Qualify`, `SameName`). No change in behaviour.
  - [ ] Stage 2: generic names and types. `AddressMessage` becomes `DeviceMessage` (name, range, roles; `midi.unit` and `midi.maxDataSize` stay with the address map); a block is a `PlanRange` (`BlockResult.Block`, `ReceivedData.Block`; `AddressBlock` stays inside the address map and `DataPlan`); `DeviceValues` and `FieldValueStore` move to `Jacobi.Midi.Device.Messages`; the shared helpers move out of `AddressProtocol`: finding the carriers of a root, `SelectBody`, the device values (`MissingDeviceValues`, `DeviceFor`), writing and reading the envelope (`EnvelopeSource`/`EnvelopeSink` for the `device.*` and `data` roles; the `address`/`size` roles filled by the address map).
  - [ ] Stage 3: the interfaces, with `AddressMap` as the only map. `IMessageMap` (`Root`, `Device`, `DataMessages`, `Message(name)`, `IsData(message)`, `Validate(range, splitBy)`, `Split`, `Write`, `TryRead`, `IsComplete(block, received)`, `CreateState()`), `IMessageMapProvider.TryCreate`, the registry (today's `AddressMaps`) with the provider chain, the cache per plan and `Validate(range, splitBy, messages, device)`; `IDeviceState` (sink and source, `Contains`, `CopyTo`, merging a send and what is missing, `Clear(range)`, `Clear()`); `ReceivedData` decodes itself (no `Decode` on the map). `MessageExchange` keeps only the exchange checks (no address terms; the split message is the first sent message, else the first received data message) and `DeviceSession` only orchestrates (`_states` by map, no `WidenToAtomic`/`FieldsOf`/`CopyValues`). No change in behaviour.
  - [ ] Stage 4: `DumpMap` for a root that is a message itself, with tests: one block (the whole root), complete after one message, a dump state per root. Add the universal Identity Request/Reply to `Midi.schema.xml` (see *General*) as the example.
  - [ ] Stage 5: `DumpMap` for a root carried as the body of an open choice, with tests: the carriers found with the serializer lookups, the body selected by device values. A root carried only inside another body is reported as not supported.
  - [ ] Stage 6: documentation: a readme for `Messages`, the readmes of `Exchange` and `Addressing` (*devices without addresses are not a concern of the address map* no longer holds), `exchange-definitions.md` (the stage 1 notes on the content binding) and `docs/analysis/korg.md`.
- [ ] **Dependent areas of the session state.** A transfer to one area can change another one on the device without the device telling: a write to the GX-700 *Sound Change Request* (or a program change) replaces the temporary area, storing a patch changes a memory item. Describe these dependencies in the schemas (a `midi.*` tag on the trigger, naming the nodes it changes) and let `DeviceSession` invalidate those nodes after the transfer completed, in the place where it updates its state after a send.
- [ ] **`midi.role="data"` is redundant on a message with one open choice.** When the exchange file names the data message, its open choice is the one that carries the range; the role only tells which open choice is meant when a message has more than one. It is still used to find the data messages without an exchange file (the reverse lookup: which messages can carry a root, e.g. for `Listen` and offline data). Decide whether the role becomes optional (required only on a message with more than one open choice) and update the checks (`AddressProtocol`, `AddressMapValidator`, `AddressMapTags`) and the schemas.

- [ ] **The message interval should be the pause on the wire.** The `messageInterval` of the exchange file is kept from the moment the connection accepted the previous message, but a MIDI 1.0 (DIN) port takes about 0.32 ms per byte (31250 baud) to transmit it: the 77 byte Common section of the GX-700 takes ~25 ms, so the next message may follow without the 20 ms pause the device needs. Add the transmission time of the message to the pause (or make it configurable per connection), in one place for `MessageExchange` and the Schema Editor's *Send*.
- [ ] **Message exchange patterns**: configurable, in exchange files, built up in steps (see the proposal [exchange-definitions.md](Exchange/exchange-definitions.md)).
  - [x] Step 1: the patterns of the old code protocols (one way, acknowledged) as exchange files (`ExchangeDefinitions`) of a map root, run by `MessageExchange.Execute` per block (`ExchangeMachine`); standard names (`ExchangeNames`); `midi.message`, `midi.exchange` and `midi.messageInterval` removed from the schemas; the session's `RequestData`/`SendData`/`Execute`; the first block that does not complete ends a transfer; the Roland GP-8 and GX-700 files; the console and the Schema Editor load the files of their assemblies.
  - [x] The exchange files in XML (`*.exchange.xml`) and JSON (`*.exchange.json`), read into the same tree so the checks are the same; the formats described by `Exchange/exchange.xsd` and `Exchange/exchange.schema.json`.
  - [x] Stage 2: `state` renamed to `turn` (`ExchangeTurn`); retries with a limit per block (`on/@retry`), the reason names the retries.
  - [ ] Roland handshake protocol: WSD/RQD → ACK → DAT → ACK … EOD, ERR → resend, RJC → abort, with retries and timeouts.
  - [ ] Boss GX700 requires change-sound-request to be sent after a parameter change (DS1) to effectuate the change.
  - [ ] Framed transactions: Yamaha Bulk Header → blocks → Bulk Footer (stored Live Set Sounds of the CP88, CK88, YC).
  - [ ] Commands without data: write/store requests (Korg Program Write Request, Yamaha Store To Flash) with their completed/error replies.
  - [ ] Device modes: requests that are only accepted in some modes (Korg i5M, DS-8 panel modes), with mode request/change messages.
  - [ ] A hook for a manual operation on the device (e.g. "press the bulk dump key"): the exchange asks the client to prompt the user and waits for the data or a cancel.
- [ ] **Windows Midi API - use of EndpointTerminalBlocks** is discuraged in favor of using function blocks. 
- [ ] **Detect the receive group of a device.** The send and receive group of a device can differ (`MidiGroupPair`): a MIDI 1.0 DIN in/out pair is two independent cables, and a MIDI 2.0 function block can be one-way. The cabling is not in the endpoint's blocks, so only a round trip finds it: `DeviceIdentity` sends the Identity Request on the send group, listens on **all** groups and returns each reply with the group it arrived on. The Schema Editor (MIDI bar) and the Console (device panel) offer a *Detect* that fills in the receive group from it.

## Address map

- [x] **A data message carries any aligned block, not only one group occurrence.** `AddressMap.CreateData` and `Decode` only handle one whole group: a few fields, one field of a larger group, or neighbouring groups in one message throw `NotSupportedException`. This also fixes `MessageExchange.Send` with a `range` message whose blocks span more than one group.
  - [x] Let an open choice target a range in Jacobi.BinarySerializer: `FromTarget`/`FromInstance` to `ToTarget`/`ToInstance` (`OpenChoiceSourceResult`/`OpenChoiceSinkResult`, `CreateOpenChoiceRange`), each a group or a field.
  - [x] Accept any aligned block in `CreateData`/`Decode` (`GroupTarget` becomes a block target), the recognition of received data (`TryRead`, `GroupTargets`) and `AddressMapAdapter` (it rejects a client's body narrowed to a range with `NotSupportedException`).
